# 技能工坊（skill-creator）

## 核心原则

**技能质量是行为属性，不是文档属性——一个技能"完成"的标志是：换一个全新的 agent，带着它明显做得比不带它好。**（蒸馏自 SkillForge）

## 第一步：分诊（任何创建动作之前）

先判断请求属于哪类，**绝不直接开造**：
- 查本机技能目录（三层：内置/用户级/工作区级 `.coworker/skills/`）与当前技能目录清单，看是否已有覆盖：
  - **强匹配已有技能** → 推荐用现有的，不创建重复技能
  - **中等匹配** → 提议"改进现有技能"（走下方改进流程）
  - **弱/无匹配 + 明确创建意图** → 进入创建流程
  - **多域需求** → 建议组合现有技能而非新建
  - **意图不明** → 先问一个澄清问题

> 反模式：重复造已有技能 = 生态垃圾。分诊永远先行。

## 创建流程（按序执行，每步不可跳）

### 0. 基线门（RED，创建新技能前强制）

**写任何东西之前**：选 1-2 个代表目标任务，在**不带技能**的情况下执行一遍，逐字记录它做错了什么。
- **如果基线没有失败 → 停止。这个技能没必要存在。**
- 基线失败点 = 技能的测试用例 + 描述关键词来源。

### 1. 分析需求

- 识别显性/隐性/发现式需求。
- 三透镜：
  - **反演**：什么必然导致失败？→ 反模式清单
  - **帕累托**：哪 20% 范围带来 80% 价值？→ 砍掉其余
  - **根因**：这是真正的问题吗？
- 明确要防的失败类型，让指令形态匹配失败形态（清单式防遗漏、规则式防违规、流程式防无序）。

### 2. 生成（规范格式）

按 QunWork 规范写 `SKILL.md`：
- **frontmatter**：`name`（与目录同名，仅 `\w-.`）、`description`、`version`、`category`（dev-workflow 等）、`author`、`tags`
- **正文**：markdown；标题 + 何时使用 + 流程步骤 + 检查清单 + 重要规则
- **体积纪律**：正文 ≤10-15KB（QunWork 渐进式披露，太大一次加载就吃满上下文）
- **不用 `allowed-tools`**：QunWork 会把它变成"仅用这些工具"的强约束，过度限制
- 深层细节放同目录参考文件（`references/`），正文保持精炼

### 3. 描述优化器（解决触发不准——本技能核心）

**描述原则（description doctrine）**：
- 只写**触发条件**：用户什么时候该用这个技能（场景 + 症状关键词 + 用户原话怎么表达）
- 写清楚**何时不用**（避免误触发）
- 第三人称；用用户可能说的关键词（"QA""找 bug""测测这个网站"）
- **绝不写工作流摘要**——agent 看到摘要会跳过正文直接按摘要执行
- 长度：QunWork description 是每轮常驻的路由面，精炼到 ≤300 字符为佳

**触发测试**：写好后用 5-10 个典型用户请求测试：
- **正例**（应该触发）：每个都应命中描述关键词
- **近失例**（不该触发）：如"review"技能 vs "帮我review一下这周的健身计划"——不应误触发
- 不命中的 → 加症状关键词；误触发的 → 加"何时不用"澄清
- **迭代依据是观察到的失败，不是凭空猜测**

### 4. 格式规范化校验（机械门）

写完后逐项检查：
- [ ] name 合法（`\w-.`，与目录一致），无空格/中文
- [ ] description 非空，含触发词 + 何时不用
- [ ] 正文非空，markdown 结构完整（frontmatter 以 `---` 正确闭合）
- [ ] 体积 ≤15KB；无 allowed-tools
- [ ] frontmatter 无多余/错误字段（QunWork 只认 name/description/version/category/author/tags/updated_at）
- [ ] 用 `load_skill` 加载一遍确认可解析（解析失败立即暴露）

### 5. 行为测试（GREEN 门）

- **重跑基线任务（带技能）**：用全新上下文执行第 0 步的任务，验证基线失败点不再出现。**行为差异是唯一标准。**
- 对已有技能的**改进**：用盲 A/B——改进版 vs 原版各跑一遍，只看结果判断哪个好，不带偏见。
- 测试通过才落盘。

### 6. 对抗审阅（质量门）

派一个**独立视角**的审阅（无偏见的二次复核，或让会话切换角色）**反驳**这个技能：哪里会误导？哪里会过度触发？它自己的场景哪里会失败？
- 被证明的问题 → 修掉
- 修完再验一遍触发测试 + 行为测试
- **不搞评审小组**——同模型的一致同意没有意义；用可证伪的 lint + 对抗反驳

### 7. 落盘 + evals（带测试发布）

- 用 `create_skill` 工具或直接写文件落盘到 skills 库（工作区级 `.coworker/skills/` 或用户级 `%APPDATA%\coworker\skills\`）
- 建 `evals/` 目录（同技能目录下）：
  - `triggers.md`：触发查询（正例 + 近失例）
  - `scenarios.md`：行为场景 + 断言（基线失败 → 期望行为）
- 后续任何修改都重跑 evals 回归——改坏了立刻暴露

## 改进已有技能流程

1. 读原 SKILL.md，明确要改的失败点（触发不准？流程缺失？体积过大？）
2. 按"描述优化器"重写描述，按规范修正格式
3. **盲 A/B**：原版 vs 新版各跑一次代表任务，对比行为差异
4. 对抗审阅 + evals 回归
5. 落盘更新（保留版本号递增，author 注明改动）

## 技能健康检查（可选）

对技能库整体体检：
- **重复**：多个技能覆盖同一能力 → 建议合并
- **触发碰撞**：两个技能 description 关键词重叠 → 建议错开
- **过期**：引用的工具/路径已不存在 → 提示更新
- **体积超标**：>15KB → 建议瘦身（细节移 references/）

## 反模式表

| 避免 | 改为 |
|---|---|
| 无失败基线就创建 | 先跑 RED 门；基线不失败 = 不需要技能 |
| 描述写工作流摘要 | 只写触发条件——agent 会按摘要执行而跳过正文 |
| 正文里写"Triggers"章节 | 只有 frontmatter description 驱动触发 |
| 审批小组 + 自评门 | 可证伪的 lint + 对抗反驳 |
| `<details>` 折叠假装渐进披露 | 独立 references/ 文件按需加载 |
| 重复造已有技能 | 第 1 步分诊先行，永远 |
| 创建后不测 | evals 带测试发布，改动即回归 |

## 交付清单

- [ ] 基线失败已捕获（RED）
- [ ] 带技能重跑清除基线失败（GREEN）
- [ ] 触发检查通过（正例命中 + 近失例不误触发）
- [ ] 格式规范校验全过 + load_skill 可加载
- [ ] 对抗审阅的已证问题修复
- [ ] evals/ 随技能发布；改动后回归通过
- [ ] 正文 ≤15KB
