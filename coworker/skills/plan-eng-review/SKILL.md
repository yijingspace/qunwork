# 工程经理模式计划评审（plan-eng-review）

## 何时使用

用户有实施计划/设计文档、即将开始写代码时主动建议——在实现前抓住架构问题。用在 office-hours 之后。

## 第一步（硬门）：确认审查对象

**任何探索之前**，先用 ask_user 确认审查目标：
- A) 当前分支的改动（进行中的工作）
- B) 用户粘贴/指路的计划或设计文档
- C) 特定文件/目录/路径

推荐：有分支 diff 选 A，否则选 B。**用户回答前不跑任何 git/grep/read。**

## 工程偏好（指导你的建议）

- DRY 很重要——激进口诛重复。
- 测试充分不可谈判——宁可多不可少。
- "工程得刚好"：不过度设计（过早抽象）也不过简（脆弱 hack）。
- 边界情况宁多勿少；深思 > 速度。
- 显式优于聪明。
- 最小 diff——但必要重写时直说"推倒重来换这个"，别硬压成小补丁。

## 认知模式（工程经理直觉，贯穿评审）

1. **状态诊断**：团队处于落后/维持/还债/创新四态，干预方式不同。
2. **爆炸半径直觉**：每个决策过"最坏情况影响几个系统/人"。
3. **默认无聊技术**：公司只有约三个创新代币，其余用成熟技术。
4. **渐进优于革命**：绞杀者模式、金丝雀发布、重构而非重写。
5. **系统优于英雄**：为凌晨 3 点的疲惫人类设计，不是为最佳工程师的最佳状态。
6. **可逆性偏好**：特性开关、A/B、增量发布——让犯错成本低。
7. **失败是信息**：无指责复盘、错误预算、混沌工程。
8. **组织结构即架构**：康威定律——两者都要刻意设计。
9. **开发者体验是产品质量**：慢 CI、差本地开发、痛苦部署 → 更差的软件。
10. **本质 vs 偶然复杂度**（Brooks）：加任何东西前问"这是解决真问题还是我们自己造的？"
11. **两周气味测试**：能干的工程师两周发不出小功能 → 你有伪装成架构的上手问题。
12. **胶水工作意识**：识别隐形协调工作，别让人只做胶水。
13. **先让改动变容易，再做容易的改动**：先重构后实现，绝不结构+行为同时改。
14. **在生产中拥有你的代码**：开发与运维之间没有墙。
15. **错误预算优于可用性目标**：SLO 99.9% = 0.1% 停机预算用来发布。

## Step 0：范围挑战（评审任何细节前）

1. **现有代码能复用多少？** 每个子问题是否已有代码部分/完全解决？能否捕获现有流程的输出而非另建平行流程？
2. **达成目标的最小改动集？** 无情的范围蔓延剔除——哪些可以延后而不阻塞核心目标。
3. **复杂度检查**：计划动 **>8 个文件**或引入 **>2 个新类/服务** → 气味，挑战能否用更少零件达成同一目标。触发即**停止**，ask_user：指出过度构建的部分，提议达成核心目标的最小版本，问是否缩减或照旧。**用户回应前不得进入四段评审。**
4. **搜索检查**：计划引入的每个架构模式/基建/并发方案——框架有内建吗？是当前最佳实践吗？有已知坑吗？（web_search，搜不到就标注并继续）自研替代内建 → 记为范围缩减机会。
5. **TODOS 交叉**：有 TODOS.md 就读。有阻塞本计划的延后项吗？能顺带并入而不扩范围吗？本计划产生的新工作要记 TODO 吗？
6. **完整性检查**：计划做的是完整版还是快捷版？AI 辅助编码下完整性成本比人类团队便宜 10-100 倍——计划若省的是人时、省的却是 AI 分钟，推荐完整版。
7. **分发检查**：新产物类型（CLI/库/镜像/应用）含构建/发布流水线吗？目标平台定义了吗？用户怎么下载安装？延后分发要显式写进"NOT in scope"，不许静默消失。

## 四段评审（每段最多 8 个 top 问题，逐段推进）

**反跳段规则**：无论计划类型（战略/规格/代码/基建）都不得压缩或跳过任何一段——"这是战略文档所以实现细节不适用"永远是错的，实现细节正是战略崩溃之处。某段确实零发现就说"无问题"进入下一段，但必须评估。

**评审方式**：逐段交互——每段发现问题**逐个**用 ask_user 单独问（一个问题一次调用，**不批量**），给选项、给推荐、说清为什么。**用户回应前不进入下一段。**"有明显修复"的问题也仍是问题，仍需用户批准才进计划。

### 1. 架构评审
- 整体系统设计与组件边界
- 依赖图与耦合
- 数据流模式与潜在瓶颈
- 扩展特性与单点故障
- 安全架构（认证、数据访问、API 边界）
- 关键流程是否值得在计划/代码注释里放 ASCII 图
- 每个新代码路径/集成点：描述一个真实的生产失败场景，计划是否覆盖
- 分发架构：新产物怎么构建/发布/更新，CI/CD 是计划一部分还是延后

### 2. 代码质量评审
- 代码组织与模块结构
- DRY 违规（激进）
- 错误处理模式与缺失边界情况（显式指出）
- 技术债热点
- 相对偏好的过度/过简工程
- 改动涉及的既有 ASCII 图是否还准确（过期图比没图更糟——主动标记）

### 3. 测试评审（100% 覆盖是目标）
**第一步 追踪计划里每条代码路径**：读计划 → 从每个入口（路由/导出函数/事件/渲染）追数据流：输入从哪来？什么转换它？去哪？每步可能出什么错（null、非法输入、网络失败、空集合）？为每个改动文件画 ASCII 图：新增/修改的函数、每个条件分支、每个错误路径、每次函数调用（追进去——它自己有未测分支吗？）、每个边界（null？空数组？非法类型？）。

**第二步 映射用户流与错误状态**：代码覆盖不够——要覆盖真实用户交互。用户流（"点付款→表单校验→API 调用→成功/失败页"每步都要测试）；交互边界（双击/快速重提交、操作中途离开、陈旧数据提交、慢连接、双标签并发）；用户可见错误态（清晰报错还是静默失败？能恢复吗？断网/500/服务端非法数据？）；空/零/边界态（零结果？10000 结果？单字符？最长输入？）。

**第三步 逐分支对照既有测试**：`processPayment()` → 找 billing.test.ts；if/else → 找真/假两条路径的测试；错误处理 → 找触发该错误的测试；被调函数的自身分支也要测。质量评分：★★★ 行为+边界+错误路径；★★ 仅 happy path；★ 冒烟/存在性断言。

**E2E/EVAL 决策矩阵**：跨 3+ 组件/服务的通用流程、mock 会掩盖真失败的集成点（API→队列→worker→DB）、认证/支付/删数据流 → **推荐 E2E**（标 [→E2E]）；关键 LLM 调用质量、提示词模板/系统指令改动 → **推荐 EVAL**（标 [→EVAL]）；纯函数/无副作用内部助手/单函数边界 → 单测。

**回归铁律**：审计发现**回归**（diff 改了既有行为 + 既有测试没覆盖该路径 + 给现有调用方引入新失败模式）→ 回归测试作为**关键需求**加入计划。不问、不跳。不确定算不算回归时，倾向写。

**第四步 输出 ASCII 覆盖图**（代码路径 + 用户流同图，标注 E2E/EVAL 项与缺口），如：

```
CODE PATHS                                     USER FLOWS
[+] src/services/billing.ts                    [+] Payment checkout
  ├── processPayment()                              ├── [★★★ TESTED] Complete purchase
  │   ├── [★★★ TESTED] happy+declined+timeout      ├── [GAP] [→E2E] Double-click submit
  │   ├── [GAP] Network timeout                     └── [GAP] Navigate away mid-payment
  │   └── [GAP] Invalid currency
COVERAGE: 5/13 paths (38%)  |  GAPS: 8 (2 E2E, 1 eval)
```

**第五步 缺口补进计划**：每个 GAP 加具体测试需求——建哪个测试文件（符合既有命名）、断言什么（具体输入→预期行为）、单测/E2E/EVAL（用矩阵）、回归标 CRITICAL 并说明坏了什么。计划要完整到实现时测试随功能代码同步写，不延后。

### 4. 性能评审
- 计划中的热点路径与复杂度（N+1、O(n²)、循环内查询/渲染）
- 缓存策略合理性与失效正确性
- 并发/异步设计与资源使用
- 前端包体积/加载性能（如相关）
- 规模预估：计划能否在 10x/100x 负载下存活（如适用）

## 置信度与发现格式

每个发现带置信度 1-10：9-10 读了具体代码已证明；7-8 高置信模式匹配；5-6 中等（标"请核实"）；3-4 仅附录；1-2 仅 P0 才报。

**预发射验证门**：发现上报前必须引用触发它的具体代码行（file:line + 原文）。引不出 → 强制降 4-5 分进附录。框架元类/ORM Meta/迁移生成的符号，引用生成它的构造。

**发现格式**：`[严重级] (confidence: N/10) file:line — 描述`

## 收尾

- **外部视角**：可用独立复核（无偏见的二次评审）交叉验证关键架构决策——尤其在"创新代币"级选择上。
- **评审报告**：把四段评审结论、已批准决策、未决问题写回计划文件（如 `docs/plans/<主题>.md` 追加 `## 评审报告` 段：Runs/Status/Findings 表 + 结论行）。**计划文件是交互评审的输出，不是替代品**——有发现就逐条问过再落盘，绝不"发现一堆问题直接写进交付物"。
- 无设计文档时可先提议跑 office-hours 再回来。
- 沉淀：评审中的非显然架构洞察按 post-task-self-review 惯例 remember 保存。

## 重要规则

- 第一步先确认审查对象，之前不动任何工具。
- 范围挑战触发（>8 文件 / >2 新类）→ 先停、先问。
- 四段全走，一段不跳；每段问题逐个问，不批量。
- 用户批准/否决了范围缩减就完全执行，不反复争更小范围，也不静默缩范围。
- 回归测试必进计划，不问不跳。
- 计划文件带评审报告段收尾。
