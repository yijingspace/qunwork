# 系统化根因排查（investigate）

## 何时使用

用户报告报错、500、堆栈、异常行为、"之前还好好的"、排查为什么停了时**主动使用**（不要直接上手改代码）。

## 铁律

**没有根因调查，就不许修复。** 修症状只会打地鼠：每个不解决根因的修复都让下一个 bug 更难找。找到根因，再修。

## Phase 1：根因调查（先收集证据，再形成假设）

1. **收集症状**：读错误信息、堆栈、复现步骤。信息不足时用 ask_user 一次只问一个问题。
2. **读代码**：从症状沿代码路径回溯找可能成因。用 grep 找所有引用点，read_file 理解逻辑。
3. **查最近改动**：`git log --oneline -20 -- <受影响文件>`。之前能用吗？改了什么？**回归 = 根因在 diff 里。**
4. **复现**：能否确定性触发？不能就继续收集证据，别往下走。
5. **查排查历史**：同一文件/区域的反复 bug 是**架构气味**而非巧合。回忆/检索此前的排查记录（remember 或知识库），判断根因是否是结构性的。

输出：**"根因假设：……"** —— 一个具体、可检验的论断（什么错了、为什么）。

## Phase 2：模式分析（对照已知模式）

| 模式 | 特征 | 查哪里 |
|---|---|---|
| 竞态条件 | 间歇性、依赖时序 | 共享状态的并发访问 |
| 空值传播 | NoMethodError / TypeError | 可选值缺守卫 |
| 状态损坏 | 数据不一致、部分更新 | 事务、回调、钩子 |
| 集成失败 | 超时、意外响应 | 外部 API、服务边界 |
| 配置漂移 | 本地好、测试/生产坏 | 环境变量、特性开关、DB 状态 |
| 陈旧缓存 | 显示旧数据、清缓存就好 | Redis、CDN、浏览器缓存 |
| 回归 | 之前能用、最近改动后坏 | 该文件的 git 历史 |

另查：TODOS.md 相关已知问题；`git log` 同区域先前的修复（反复修同一文件 = 架构问题）。

**外部检索**：不匹配已知模式时用 web_search 查 "{框架} {通用错误类型}"——**先脱敏**：去掉主机名、IP、文件路径、SQL、客户数据，只搜错误类别，不搜原始报错串。搜不到就跳过，继续假设验证。

## Phase 3：假设验证（写任何修复前先验证）

1. **确认假设**：在疑似根因处加临时日志/断言/调试输出，跑复现。证据吻合吗？
2. **假设错了**：回到 Phase 1 收集更多证据。**不要猜。** 换新假设前再考虑一次外部检索（同样先脱敏）。
3. **三振出局**：3 个假设都失败 → **停止**，用 ask_user：

```
已测 3 个假设均不匹配，这可能是架构问题而非简单 bug：
A) 继续排查——我有新假设：[描述]
B) 升级给人审——需要熟悉系统的人介入
C) 加日志等复现——给该区域埋点，下次抓到
```

**红旗（见到就减速）**：
- "先快速修一下"——没有"先"。修对了或升级，别无他途。
- 没追数据流就提修复方案——你在猜。
- 每个修复都引出新问题——错层了，不是错代码。

## Phase 4：实现

根因确认后：

1. **修根因，不修症状**。消除实际问题的**最小**改动。
2. **最小 diff**：最少文件、最少行数。忍住重构相邻代码的冲动。
3. **写回归测试**：无修复时**失败**（证明测试有意义），有修复时**通过**（证明修复有效）。
4. **跑全量测试**，粘贴输出。不允许有回归。
5. **改动 >5 个文件**时用 ask_user 提示爆炸半径：

```
这个修复涉及 N 个文件，对 bug 修复来说爆炸半径偏大：
A) 继续——根因确实横跨这些文件
B) 拆分——先修关键路径，其余延后
C) 重想——也许有更聚焦的方案
```

## Phase 5：验证与报告

**新鲜验证**：重新复现原始 bug 场景，确认已修复。这不是可选项。

跑测试套件并粘贴输出。输出结构化调试报告：

```
DEBUG REPORT
════════════════════════════════════════
Symptom:         [用户观察到的现象]
Root cause:      [实际错在哪]
Fix:             [改了什么，带 file:line 引用]
Evidence:        [测试输出、复现尝试证明修复有效]
Regression test: [新测试的 file:line]
Related:         [TODOS.md 项、同区域先前的 bug、架构备注]
Status:          DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

**沉淀**：按 post-task-self-review 惯例——非显然的根因模式/坑用 remember 保存（含受影响文件，供未来同区域排查检索）；可复用的排查模式可在本技能中补充。

## 重要规则

- **3 次以上修复尝试失败 → 停下来质疑架构**。是架构错了，不是假设错了。
- **绝不应用无法验证的修复**。不能复现并确认，就不要交付。
- **绝不说"这应该能修好"**。验证并证明它。跑测试。
- **改动 >5 文件 → 先问爆炸半径**。
- **完成状态**：
  - DONE —— 找到根因、应用修复、写好回归测试、全部测试通过
  - DONE_WITH_CONCERNS —— 已修但无法完全验证（如间歇性 bug、需 staging）
  - BLOCKED —— 调查后根因不明，已升级
