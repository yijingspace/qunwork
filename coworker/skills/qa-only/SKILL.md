# QA 报告模式（qa-only）

## 何时使用

用户要求测网站/应用但**只要报告**，或修复由别人/其他流程处理时。测试-修复-验证闭环请用 qa 技能。

## 与 qa 的核心差异

**绝不修复 bug。** 只发现、只记录。不读源码、不编辑文件、报告中不给修复建议。你的工作是报告什么坏了，不是修好它。

**无测试框架提示**：若项目无测试基础设施，在报告摘要中注明："未检测到测试框架。运行 qa 可引导搭建并启用回归测试生成。"

其余方法论与 qa 技能相同（见下）。

## 参数与模式

| 参数 | 默认 | 说明 |
|---|---|---|
| 目标 URL | 自动探测 | 给了用 URL；没给且在功能分支上 → diff-aware 模式 |
| 档位 | Standard | `--quick` 只报 critical+high；`--exhaustive` 全报 |

**浏览器工具映射（QunWork）**：`browser_open_url` 打开、`browser_snapshot` 读页面与可交互元素、`browser_screenshot` 截图留证、`browser_click`/`browser_type`/`browser_select` 操作、`browser_wait` 等待。

## 模式

- **Diff-aware**（无 URL 且在有改动的分支）：`git diff main...HEAD --name-only` + commit log 分析改动 → 推受影响页面/路由 → 探测本地应用（localhost:3000/4000/8080）→ 逐页测试 → 对照意图验证。
- **Full**（给了 URL）：系统性探索每个可达页面，记录 5-10 个有充分证据的问题，产出健康评分。
- **Quick**（30 秒冒烟）：首页 + 顶部 5 个导航目标，只查加载/控制台报错/坏链。

## 探索流程（每页）

打开页面 → 截图 → 查控制台 → 逐页检查清单：
1. 视觉扫描（布局）
2. 交互元素（按钮/链接/控件）
3. 表单（填+提交；测空、非法、边界值）
4. 导航（进出路径）
5. 状态（空态、加载、错误、溢出）
6. 控制台（交互后新报错）
7. 响应式（移动视口，如相关）

**框架提示**：Next.js 查 hydration 报错与 `_next/data` 404；Rails 查 N+1 警告与 CSRF token；SPA 用 snapshot 找导航（链接列表会漏客户端路由），查陈旧状态（离开再回来数据刷新吗？）、浏览器前进/后退、内存泄漏。

## 健康评分 Rubric（0-100 加权）

| 类别 | 权重 | 计分 |
|---|---|---|
| 控制台 | 15% | 0 错=100；1-3=70；4-10=40；10+=10 |
| 链接 | 10% | 0 坏=100；每个坏链 -15（最低 0） |
| 视觉/功能/UX/性能/内容/无障碍 | 其余 | 每项从 100 起：Critical -25、High -15、Medium -8、Low -3 |

`总分 = Σ(分类分 × 权重)`，各分类最低 0。存 `baseline.json`（日期/URL/分数/问题清单/分类分）供 regression 模式对比。

## 报告结构

报告 md 文件（如 `qa-reports/qa-report-<域>-<日期>.md`）：
- 元数据：日期、时长、访问页数、截图数、框架
- 问题清单（发现即写，不攒批）：严重级、类别、页面、复现步骤（引用截图）
- 控制台健康汇总
- **Top 3 待修项**（按严重级最高的 3 个）
- 健康评分（基线 → 本次，regression 模式含对比：修了哪些、新增哪些、分数变化）
- 无测试框架时附提示行

## 重要规则

1. **复现至上**：每个问题至少一张截图，无例外。
2. **先验证再记录**：问题重试一次确认可复现。
3. **绝不写凭据**：复现步骤里密码写 `[REDACTED]`。
4. **增量写报告**：发现问题立刻追加。
5. **不读源码来测试**：以用户视角，不当开发者。
6. **每次交互后查控制台**：不显形的 JS 报错也是 bug。
7. **像用户一样测**：真实数据，完整端到端流程。
8. **深度优于广度**：5-10 个有充分证据的问题 > 20 个模糊描述。
9. **绝不删输出文件**：截图与报告累积是有意的。
10. **绝不拒绝开浏览器**：用户要 QA 就是要浏览器实测；diff 看似无 UI 改动也要测。
11. **绝不修复**——只报告；不读源码、不改文件、不给修复建议。
12. **沉淀**：QA 中发现的非显然模式/坑按 post-task-self-review 惯例用 remember 保存。
