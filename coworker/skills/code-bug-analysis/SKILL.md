# 代码漏洞与BUG分析

自动识别编程语言、分类风险等级、提供修复方案;支持工程代码安全审计和竞赛算法分析。

## 何时使用

- 用户提交代码要求"审查 / 找漏洞 / 分析 bug / 安全审计"
- 用户要求分析算法代码(竞赛题解、复杂算法、边界情况)
- 任务涉及代码质量、潜在缺陷、安全风险排查

## 分析流程

1. **识别语言与代码类型**:先确定编程语言(依据扩展名、语法特征、依赖清单),并判断是**工程代码**(业务系统、生产服务)还是**竞赛代码**(算法题解、单文件解题)——两者风险侧重点不同,不要误判。
2. **并行分析**:将代码按模块/函数拆分,并行启动多个分析视角(安全漏洞、逻辑缺陷、性能问题、边界情况),**不要串行逐个分析**。
3. **去重合并**:合并多个视角的重复发现(同一漏洞的不同表现只保留一条,汇总触发路径),**不要原样罗列重复项**。
4. **风险分级**:每个发现按严重级别分类——CRITICAL(可利用漏洞/数据泄露/崩溃)、HIGH(明显缺陷/常见攻击面)、MEDIUM(潜在问题/边界错误)、LOW(风格/健壮性建议)。
5. **生成修复方案**:对 CRITICAL/HIGH 发现必须给出修复方案与**修复前后代码对比**(before/after),**不得跳过**。
6. **生成最终报告**:使用统一输出格式(见下),包含风险分级、后果说明、修复对比。

## 输出格式

对每个发现使用统一结构:

```
### [CRITICAL|HIGH|MEDIUM|LOW] <发现标题>
- **位置**: <文件>:<行号范围> / <函数名>
- **原始代码摘要**: <关键片段,必须包含原始代码,不能只给结论>
- **后果**: <不修复会怎样 — 具体到数据、权限、运行时行为>
- **修复方案**: <如何修复,1-3 步>
- **修复对比**:
  ```diff
  - <修复前>
  + <修复后>
  ```
```

报告结尾给**汇总表**(发现数按级别统计)与**优先级建议**(哪些必须先修)。

## 编程语言识别规则

- 依据扩展名优先(如 `.py`→Python、`.js/.ts`→JS/TS、`.go`→Go、`.rs`→Rust、`.java`→Java、`.cpp/.c`→C/C++);无扩展名时依据语法特征(缩进+`def`→Python、`package main`→Go、`fn main`→Rust)。
- **不要无证据猜测语言**——拿不准时说明依据或请用户确认。

## 工程代码 vs 竞赛代码

| 维度 | 工程代码 | 竞赛代码 |
|---|---|---|
| 关注点 | 安全(注入/XSS/权限)、错误处理、并发、依赖 | 算法正确性、复杂度、边界情况、溢出 |
| 重点检查 | 输入校验、鉴权、资源释放、异常路径 | 大输入、极端值、空集/单元素、整数溢出 |
| 修复方式 | 补防御、加校验、重构 | 优化算法、补边界分支 |

**注意**:竞赛代码误判为工程代码(反之亦然)会导致检查方向错误——先确认类型再分析。

## 对初学者的沟通

- 对初学者避免过于技术性的语言:每个 CRITICAL/HIGH 用一句话解释"为什么这是问题"。
- 对关键漏洞(如注入、越权、密钥泄露)明确提醒用户**自行验证后再上线**,不要替用户做"安全结论"。

## 反模式清单(Anti-Patterns)

以下做法**禁止**:

| 违规行为 | 严重级别 |
|---|---|
| 串行启动分析 Agent 而非并行启动 | CRITICAL |
| 在所有 Agent 完成前展示结果 | CRITICAL |
| 不进行去重合并重复发现 | HIGH |
| 对 CRITICAL/HIGH 发现跳过修复生成 | HIGH |
| 无证据地猜测语言类型 | HIGH |
| 修复 bug 时重构无关代码 | HIGH |
| 对初学者使用过于技术性的语言 | MEDIUM |
| 不包含原始代码摘要的发现报告 | MEDIUM |
| 忽视用户提供的上下文信息 | MEDIUM |
| 对关键漏洞不提醒用户自行验证 | HIGH |
| 竞赛代码误判为工程代码(反之亦然) | MEDIUM |
| 忽略竞赛代码的边界情况检测 | MEDIUM |
